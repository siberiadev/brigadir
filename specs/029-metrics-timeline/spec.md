# Feature Specification: Страница /metrics — кумулятивная статистика на графиках

**Feature Branch**: `029-metrics-timeline`

**Created**: 2026-07-22

**Status**: Draft

**Input**: User description: "Страница /metrics — кумулятивная статистика системы на графиках, с разбивкой по 5 вкладкам (Обзор, Расходы и токены, Здоровье прогонов, Активность и триггеры, Люди в контуре); общие фильтры сверху (период, воркспейс/борда, executor_type), данные группируются по дням за выбранный период."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Обзор состояния системы одним взглядом (Priority: P1)

Оператор/тимлид открывает `/metrics` и сразу — без выбора вкладки — видит сводку ключевых показателей платформы за выбранный по умолчанию период: сколько потрачено, сколько прогонов и с каким результатом, какой процент успешных, сколько открытых задач на людях.

**Why this priority**: Это самый частый сценарий использования страницы — быстрая проверка "всё ли в порядке" без необходимости разбираться, в какой вкладке искать нужную цифру. Без этого у страницы нет самостоятельной ценности сверх уже существующих точечных виджетов (Home-плитки, cost на Runs).

**Independent Test**: Открыть `/metrics` без дополнительных действий — вкладка «Обзор» открыта по умолчанию и показывает непустые (или явно нулевые) карточки/мини-графики по каждой из остальных четырёх групп метрик за период по умолчанию.

**Acceptance Scenarios**:

1. **Given** пользователь переходит на `/metrics` впервые за сессию, **When** страница загружается, **Then** открыта вкладка «Обзор» с карточками: суммарный расход за период, количество прогонов по статусам (компактно), success rate, медианная длительность прогона, число открытых задач на людях.
2. **Given** пользователь на вкладке «Обзор», **When** он меняет период (24ч/7д/30д) в общем фильтре, **Then** все карточки на «Обзоре» пересчитываются под новый период без перезагрузки страницы.
3. **Given** в системе за выбранный период нет ни одного прогона (например, только что развёрнутый инстанс), **When** открывается «Обзор», **Then** карточки показывают нулевые/пустые значения с понятным поясняющим текстом, а не ошибку и не бесконечную загрузку.

---

### User Story 2 - Анализ расходов и токенов по провайдерам (Priority: P1)

Человек, ответственный за бюджет, открывает вкладку «Расходы и токены», чтобы увидеть динамику расходов по дням, разбивку по типу исполнителя (executor_type) и по воркспейсам/бордам — чтобы понять, куда уходят деньги и не растут ли расходы аномально.

**Why this priority**: Расход в валюте — самая прямая и часто запрашиваемая метрика в подобных внутренних инструментах; она уже частично покрыта на Runs-странице (суммой за период), но без динамики по дням и без сравнения по бордам.

**Independent Test**: На вкладке «Расходы и токены» с периодом «7 дней» и без фильтра по воркспейсу — виден график расхода по дням со стеком по executor_type и топ воркспейсов/бордов по расходу за период.

**Acceptance Scenarios**:

1. **Given** есть прогоны за последние 7 дней с разными `executor_type`, **When** открыта вкладка «Расходы и токены» с периодом «7 дней», **Then** график расхода по дням показывает стек с сегментами по каждому встречавшемуся `executor_type`.
2. **Given** прогон выполнен исполнителем, для которого стоимость не биллинговая (не Anthropic), **When** его расход отображается на графике/в подсказке, **Then** рядом есть понятная пометка о том, что сумма оценочная (не биллинговая), как и на существующей странице прогонов воркспейса.
3. **Given** пользователь выбирает конкретный воркспейс/борду в общем фильтре, **When** данные вкладки обновляются, **Then** все графики вкладки показывают расход только по выбранному воркспейсу, а разбивка «по воркспейсам/бордам» перестаёт быть содержательной и скрывается или показывает один элемент.
4. **Given** есть прогоны с ненулевыми токенами всех четырёх типов (input/output/cache-read/cache-creation), **When** открыт график токенов по дням, **Then** каждый тип токенов виден как отдельная величина (например, отдельные линии/сегменты), без смешения в одну сумму.

### User Story 3 - Оценка надёжности прогонов во времени (Priority: P2)

Разработчик, отвечающий за пайплайн, открывает вкладку «Здоровье прогонов», чтобы увидеть, растёт ли доля падений/таймаутов со временем, как меняется длительность прогона и совпадают ли всплески отказов с конкретным `executor_type`.

**Why this priority**: Важно для операционного мониторинга, но менее частый сценарий, чем проверка расходов и общий обзор — обычно используется при расследовании конкретной деградации, а не в ежедневном режиме.

**Independent Test**: На вкладке «Здоровье прогонов» с периодом «30 дней» виден график количества прогонов по статусам по дням, отдельный график success rate по дням и график медианной/p95 длительности по дням.

**Acceptance Scenarios**:

1. **Given** за период есть прогоны во всех статусах (succeeded/failed/timed_out/cancelled/awaiting_human/queued/running), **When** открыт график количества прогонов по статусу по дням, **Then** каждый статус виден как отдельный сегмент, дни без прогонов конкретного статуса показывают нулевой сегмент, а не разрыв графика.
2. **Given** выбран конкретный `executor_type` в общем фильтре, **When** просматривается разбивка failed/timed_out по executor_type, **Then** отображаются данные только по выбранному исполнителю (аналогично сценарию с фильтром по воркспейсу).
3. **Given** прогон ещё не завершён (`finished_at` пусто), **When** считается длительность и success rate за период, **Then** такой прогон не искажает статистику длительности (не считается как что-то с нулевой/некорректной длительностью) и учитывается в подсчёте по статусам как «running»/«queued».

---

### User Story 4 - Понимание источников активности и распределения по агентам/бордам (Priority: P3)

Тимлид открывает вкладку «Активность и триггеры», чтобы понять, что чаще запускает прогоны (вебхуки, ручной запуск, поллер, ретраи после человеческого ответа), как распределена нагрузка по ролям агентов и по бордам — для планирования дальнейшей автоматизации.

**Why this priority**: Полезная аналитическая метрика, но с наименьшей срочностью — не завязана на инциденты или бюджет, скорее для периодического ретроспективного анализа.

**Independent Test**: На вкладке «Активность и триггеры» виден график количества прогонов по дням с разбивкой по `trigger_event.source`, отдельно — по роли агента, отдельно — по воркспейсу/борде.

**Acceptance Scenarios**:

1. **Given** прогоны за период инициированы разными источниками (manual/webhook/poll/rework/human-resume/triage/answer-triage/workspace-setup), **When** открыт график активности по триггерам, **Then** каждый источник виден как отдельная категория с понятной подписью на русском или общепринятым техническим термином, согласованным с остальным UI.
2. **Given** у прогона роль агента, инициировавшего его, не определена (граничный случай), **When** считается разбивка по роли агента, **Then** такой прогон попадает в явную категорию «не определено», а не пропадает молча из общего количества.

---

### User Story 5 - Мониторинг задач с участием людей (Priority: P3)

Человек, отвечающий за операционную нагрузку команды, открывает вкладку «Люди в контуре», чтобы увидеть, как быстро закрываются задачи, требующие участия человека, и не растёт ли очередь открытых задач.

**Why this priority**: Затрагивает меньшую часть общего потока (не каждый прогон уходит в `awaiting_human`), востребована реже, чем расходы или общая надёжность.

**Independent Test**: На вкладке «Люди в контуре» виден график латентности резолюции задач по дням (медиана/p95), график открытых/закрытых задач по дням и доля прогонов, ушедших в ожидание человека, по дням.

**Acceptance Scenarios**:

1. **Given** есть задачи для людей, часть из которых ещё не резолвлена (`resolved_at` пусто), **When** считается латентность резолюции по дням, **Then** в расчёт медианы/p95 попадают только резолвленные задачи, а количество ещё открытых отображается отдельной метрикой.
2. **Given** выбран период, за который не было ни одной задачи для людей, **When** открыта вкладка, **Then** графики показывают пустое состояние с понятным текстом, а не ошибку.

---

### Edge Cases

- Что происходит, если за выбранный период данных нет вообще ни по одной метрике (новый воркспейс, только что настроенный executor)? → Пустое состояние с понятным сообщением на каждой карточке/графике, без ошибок и без бесконечных спиннеров.
- Что происходит, если прогон длится дольше одного календарного дня (пересекает границу суток)? → Прогон учитывается в дне, к которому относится соответствующее событие метрики (например, для «расходов по дням» и «активности по дням» — день `created_at`; для «длительности» — день завершения); правило должно быть одинаковым для всех графиков, использующих `created_at` как якорь дня.
- Что происходит при одновременном применении фильтра по воркспейсу и по executor_type, если такая комбинация не встречается в данных за период? → Явное пустое состояние на затронутых графиках, а не ошибка запроса.
- Что происходит с прогонами без привязки к тикету (`ticket_id` пустой, setup-прогоны)? → Они учитываются в общих метриках (расход, статус, длительность), но не участвуют в срезах, требующих тикета/борды, если у них также нет `workspace_id` — такие прогоны попадают в категорию «не определено» на соответствующих графиках.
- Что происходит, если пользователь переключает вкладку до того, как данные предыдущей вкладки полностью загрузились? → Переключение не блокируется; недогруженная вкладка продолжает подгружать данные независимо в фоне.
- Что происходит с производительностью при периоде «30 дней» и большим количеством прогонов? → Данные приходят агрегированными по дням (не построчно), так что объём ответа не растёт линейно с количеством прогонов — см. FR-013.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять страницу `/metrics`, доступную из общей навигации дашборда, с пятью вкладками: «Обзор», «Расходы и токены», «Здоровье прогонов», «Активность и триггеры», «Люди в контуре».
- **FR-002**: При открытии `/metrics` по умолчанию ДОЛЖНА быть открыта вкладка «Обзор».
- **FR-003**: Страница ДОЛЖНА предоставлять общие фильтры, применяемые ко всем вкладкам одновременно: период (варианты: 24 часа / 7 дней / 30 дней, по умолчанию — 7 дней), воркспейс/борда (по умолчанию — «все»), тип исполнителя/executor_type (по умолчанию — «все»).
- **FR-004**: Изменение любого общего фильтра ДОЛЖНО обновлять данные без полной перезагрузки страницы: активная вкладка пересчитывается немедленно, остальные вкладки — при следующем открытии (ленивая загрузка панелей, см. Assumptions). Выбранные фильтры сохраняются при переключении вкладок.
- **FR-005**: Все графики, показывающие динамику во времени, ДОЛЖНЫ группировать данные по бакетам времени в единой таймзоне для всей страницы (см. Assumptions) за выбранный период, включая бакеты без данных как нулевые точки, а не пропуски. Гранулярность бакета адаптивна: период 24h — почасовые бакеты (суточный бакет на 24h вырождается в 1–2 точки), периоды 7d и 30d — посуточные («по дням»).
- **FR-005a**: Ряд, отражающий длительность прогонов (median/p95), ДОЛЖЕН относить прогон к бакету по времени ЗАВЕРШЕНИЯ (`finished_at`), а не постановки в очередь — прогон, пересёкший границу суток, попадает в бакет дня завершения. Все прочие ряды используют `created_at` как якорь бакета.
- **FR-006**: Вкладка «Обзор» ДОЛЖНА показывать компактную сводку: суммарный расход за период, количество прогонов по статусам, success rate (%), медианную длительность завершённых прогонов, количество открытых задач на людях (`human_tasks` без `resolved_at`) — с учётом применённых общих фильтров, за исключением фильтра `executor_type` для карточки открытых задач на людях (см. FR-011a).
- **FR-007**: Вкладка «Расходы и токены» ДОЛЖНА показывать: расход по дням с разбивкой по `executor_type`; суммарные токены по дням с разбивкой по типу (input/output/cache-read/cache-creation); расход по воркспейсам/бордам за период (топ, при отсутствии фильтра по конкретному воркспейсу); средний расход на прогон по дням.
- **FR-008**: Для исполнителей, чья стоимость не является биллинговой величиной (сейчас: kimi, deepseek_api), система ДОЛЖНА визуально помечать эти данные как оценочные — с текстом/меткой, согласованной с существующей пометкой на странице прогонов воркспейса.
- **FR-009**: Вкладка «Здоровье прогонов» ДОЛЖНА показывать: количество прогонов по статусу по дням; success rate (%) по дням, посчитанный как доля `succeeded` среди завершённых прогонов (succeeded+failed+timed_out+cancelled) за день; медианную и p95 длительность завершённых прогонов по дням; долю прогонов с `attempt > 1` (retry rate) по дням; разбивку failed/timed_out по `executor_type`.
- **FR-010**: Вкладка «Активность и триггеры» ДОЛЖНА показывать количество прогонов по дням с тремя независимыми разбивками: по источнику триггера (`trigger_event.source`), по роли инициировавшего агента, по воркспейсу/борде.
- **FR-011**: Вкладка «Люди в контуре» ДОЛЖНА показывать: латентность резолюции задач для людей (медиана/p95 по дням, считается только по резолвленным задачам); количество открытых и закрытых задач по дням с разбивкой по `kind`; долю прогонов, находящихся в статусе `awaiting_human`, по дням. Формулировка «сейчас в ожидании человека» (текущий статус), а не «когда-либо уходил в ожидание» — историческая доля переходов в v1 не считается (нет лога переходов статуса, см. Assumptions).
- **FR-011a**: Метрики вкладки «Люди в контуре» и карточка открытых задач на людях на «Обзоре» НЕ фильтруются по `executor_type`: у сущности `human_tasks` нет измерения типа исполнителя. При выборе `executor_type` в общем фильтре эти метрики остаются на уровне периода/воркспейса, а элемент фильтра `executor_type` на вкладке «Люди в контуре» ДОЛЖЕН быть визуально неактивен (или явно помечен как неприменимый), чтобы не создавать впечатление применённого, но игнорируемого фильтра.
- **FR-012**: Незавершённые прогоны (без `finished_at`) НЕ ДОЛЖНЫ искажать метрики длительности, но ДОЛЖНЫ учитываться в подсчётах по статусам (`queued`/`running`).
- **FR-013**: Данные для графиков ДОЛЖНЫ передаваться на фронтенд в предагрегированном по дням виде (система не передаёт построчные данные по каждому прогону для отрисовки графика) — время отклика страницы не должно расти линейно с общим числом прогонов в системе.
- **FR-014**: Прогоны без применимого измерения для конкретного среза (например, без `workspace_id` при разбивке по борде, без определённой роли агента при разбивке по роли) ДОЛЖНЫ попадать в явную категорию «не определено», а не быть молча исключены из общих сумм.
- **FR-015**: Доступ к `/metrics` и её данным ДОЛЖЕН соответствовать текущей модели доступа дашборда (тот же уровень авторизации, что и у остальных страниц дашборда), без отдельных ролей/прав специально для статистики.
- **FR-016**: При отсутствии данных за выбранную комбинацию фильтров каждая карточка/график ДОЛЖНА показывать явное пустое состояние с поясняющим текстом, а не ошибку или неопределённо долгую загрузку.
- **FR-017**: Пометки (label) для `executor_type`, статусов прогона, источников триггера и ролей агентов на графиках ДОЛЖНЫ быть согласованы с тем, как эти же значения подписаны в остальном дашборде (Runs, Home), чтобы избежать расхождений в терминологии.

### Key Entities *(include if feature involves data)*

- **Прогон (run)**: единица работы агента; для метрик значимы — время постановки в очередь/старта/завершения, статус, стоимость, использование токенов, тип исполнителя, номер попытки, исход, источник запуска, связь с воркспейсом/бордой и агентом.
- **Задача для человека (human task)**: запрос на участие человека, порождённый прогоном; для метрик значимы — тип задачи, время создания и время резолюции (если резолвлена).
- **Агент**: действующее лицо, инициирующее прогон; для метрик значима роль агента как измерение среза.
- **Воркспейс/борда**: контекст, в котором выполняются прогоны; для метрик значима привязка прогона к воркспейсу/борде как измерение среза и как значение общего фильтра.
- **Период отчёта**: выбранный пользователем временной диапазон (24ч/7д/30д), определяющий границы всех агрегаций на странице.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь может получить ответ на вопрос "сколько потрачено за последние 7 дней и по какому исполнителю" не более чем за 10 секунд с момента открытия `/metrics` (без предварительного знания, где искать эту цифру в других разделах дашборда).
- **SC-002**: Переключение между любыми двумя вкладками страницы происходит без полной перезагрузки страницы и без потери выбранных общих фильтров.
- **SC-003**: При изменении общего фильтра (период/воркспейс/executor_type) все пять вкладок отражают согласованные данные — если открыть один и тот же прогон в двух разных разрезах (например, в «Обзоре» и в «Здоровье прогонов»), суммарные показатели не противоречат друг другу.
- **SC-004**: Страница остаётся пригодной к использованию (отклик на смену фильтра — не более нескольких секунд) независимо от того, сколько всего прогонов накопилось в системе за всю историю, при выборе периода 30 дней.
- **SC-005**: 100% графиков и карточек на странице корректно отображают пустое состояние (без ошибок и зависаний) при отсутствии данных за выбранную комбинацию фильтров.

## Assumptions

- Пользователи страницы — участники команды, уже имеющие доступ к дашборду; отдельная авторизация или ролевая модель для `/metrics` не вводится (используется существующий механизм доступа дашборда).
- Группировка по бакетам использует единую таймзону UTC для всей страницы (агрегация явно в UTC — `date_trunc(..., 'UTC')`/`AT TIME ZONE 'UTC'`, не полагаясь на session TimeZone контейнера); отображение в локальной таймзоне браузера пользователя не входит в обязательный объём v1.
- Гранулярность бакета фиксирована периодом (24h→час, 7d/30d→день, FR-005); произвольная гранулярность и произвольный диапазон дат в v1 не поддерживаются.
- Фильтр `executor_type` неприменим к метрикам, производным от `human_tasks` (FR-011a): у этой сущности нет типа исполнителя, а связь `human_tasks.run_id → runs` нестабильна (`run_id` nullable). Такие метрики фильтруются только периодом и воркспейсом.
- `awaiting_human_share` в v1 приближается текущим статусом прогона (`status='awaiting_human'`), а не историей переходов: лога переходов статуса в системе нет (конституция I: durable-состояние прогона в Postgres — это ТЕКУЩИЙ статус, не журнал переходов). Точная историческая доля — вне v1.
- Период ограничен тремя вариантами (24ч/7д/30д) по аналогии с уже существующим выбором периода на странице прогонов воркспейса; произвольный диапазон дат не входит в v1.
- Метрики считаются на основе существующих полей `runs`, `human_tasks`, `agents`, `workspaces` — без введения новых таблиц или миграций схемы для v1.
- "Оценочная" (не биллинговая) стоимость для исполнителей вроде kimi/deepseek_api остаётся такой же по смыслу, как уже реализовано на странице прогонов воркспейса — эта фича не меняет способ расчёта `cost_usd`, только визуализирует уже сохранённое значение.
- Экспорт графиков (в изображение/CSV) и настраиваемые дашборды (сохранение своих наборов графиков) не входят в v1.
- Real-time обновление графиков (без действия пользователя) не входит в v1 — данные обновляются при смене фильтра или ручном обновлении страницы.
