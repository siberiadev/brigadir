# Feature Specification: Agent Identity — persona name, role, and routing key

**Feature Branch**: `014-agent-identity`

**Created**: 2026-07-16

**Status**: Draft

**Input**: User description: "Separate an agent's identity from its presentation, and make team assembly feel alive. `id` (UUID, exists) stays the true immutable identity for all internal references. `name` becomes an invented persona name (Achilles, Atalanta, Hera) — presentation only, no longer unique, no longer used for routing. `role` (new) is the function (Developer/QA/Reviewer/Planner; orchestrator = teamlead). `key` (new, NOT NULL) is a readable unique handle at the LLM/UI boundary, derived once at creation via a single canonical slug function `slugifyAgentKey(name, role)`, UNIQUE(workspace_id, key), immutable on edit, resolved to `id` at the boundary. During team generation the orchestrator picks one random theme per workspace (no hardcoded theme list) and assigns each agent a themed name + role; the system derives the key. Full scan for agents.name-as-identity → migrate to id (internal) / key (LLM/UI boundary). Migration + backfill, architecture.md §3 sync, tests in the same iteration."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Stable identity: routing by key, references by id (Priority: P1)

Today an agent's display name is also its identity: it is unique per workspace, the orchestrator routes rework by echoing it, and internal lookups (including the orchestrator's own seed) find rows by name. This story splits that into three fields: `id` (immutable internal identity, already exists), `key` (immutable readable handle used wherever the value passes through an LLM or a URL/log), and `name` (freely editable display text). The orchestrator's roster presents each worker's key, name, role, and description; a "routed" decision names the target by key; the system resolves that key to the agent's id immediately and continues internally by id only.

**Why this priority**: This is the load-bearing change — every other story builds on the new columns and the key→id resolution. It also removes a real fragility: an LLM reliably echoes a short slug but mangles UUIDs, and today a rename of an agent silently breaks nothing only because renames are effectively forbidden by the uniqueness/lookup coupling.

**Independent Test**: Create a workspace with two workers, fail a run so triage fires, have the orchestrator return `routing.target_agent = "<worker-key>"`, and observe the rework run created for the correct agent id. Rename the worker's persona mid-flight and confirm nothing breaks.

**Acceptance Scenarios**:

1. **Given** an agent created with name "Hera" and role "Reviewer", **When** the row is persisted, **Then** its key is exactly `hera-reviewer`, generated by the system (never supplied by an LLM or a client), and is unique within the workspace.
2. **Given** a triage handoff, **When** the roster is rendered for the orchestrator, **Then** each enabled non-orchestrator worker appears with its key, name, role, and description, and the prose instructs the orchestrator to route by key.
3. **Given** the orchestrator returns outcome "routed" with `target_agent` equal to an existing worker's key, **When** the system processes the report, **Then** it resolves the key to the agent's id at that boundary and the rework run references the agent by id.
4. **Given** the orchestrator returns a `target_agent` that matches no enabled worker key in the workspace, **When** the system processes the report, **Then** it escalates to a human task (same behavior as today's unknown routing target) rather than guessing.
5. **Given** an existing agent, **When** its name and/or role are edited through any update path, **Then** its key is unchanged — the update path cannot modify the key even if a key value is supplied.
6. **Given** two agents in the same workspace, **When** both are given the persona name "Hera" (different roles), **Then** both saves succeed — name is no longer unique — while their keys remain distinct.
7. **Given** the codebase after this feature, **When** scanning for uses of the agent name as an identifier (lookups, conflict targets, joins, dedup keys), **Then** none remain: internal references use id, LLM/human-boundary references use key.

### User Story 2 - Themed team generation ("alive" team assembly) (Priority: P2)

When a user asks BRIGADIR to generate a team for a board (via the admin plane's "generate agents" flow), the generation step invents ONE random theme for the workspace (Ancient Greece, movie heroes, The Matrix, superheroes, …) and gives every proposed agent a themed persona `name` plus a functional `role`. The theme is chosen by the model at generation time — there is no hardcoded theme list in the product, so themes genuinely vary between workspaces. The system, not the model, derives each agent's key from the proposed name + role.

**Why this priority**: This is the user-visible payoff ("make team assembly feel alive"), but it is meaningless without Story 1's identity split, so it lands second.

**Independent Test**: Run team generation twice against two workspaces and confirm each proposal carries themed persona names + roles under a single coherent theme per workspace, that keys were derived system-side, and that persona names within one proposal are distinct.

**Acceptance Scenarios**:

1. **Given** a team-generation request for a workspace, **When** the proposal is produced, **Then** every proposed agent has a persona `name` and a functional `role`, all names within the team follow one coherent theme, and no agent proposal contains a key (the model never emits keys).
2. **Given** a generated team is accepted and written, **When** agents are created, **Then** each key is derived by the canonical rule from name + role, and uniqueness within the workspace is guaranteed (numeric suffix `-2`, `-3`, … on collision).
3. **Given** the in-run team-setup path (the orchestrator's setup run proposing a team via its completion report), **When** the team is applied, **Then** the same acceptance holds: model supplies name + role only, system derives and de-duplicates keys.
4. **Given** a proposed persona name that yields an empty slug (e.g. a name written entirely in non-Latin script), **When** the key is derived, **Then** the system falls back deterministically (role-only slug, then a generic stem) and still produces a non-empty unique key.

### User Story 3 - Persona shown to humans everywhere (Priority: P3)

Dashboard pages, Jira comments, and other human-facing text present agents as a persona with a function — "Hera (Reviewer)" — instead of a bare technical name. The key is visible in the UI as a read-only technical identifier (useful for logs and URLs), and editing an agent's name or role from the dashboard never changes its key.

**Why this priority**: Pure presentation on top of Stories 1–2; valuable but nothing else depends on it.

**Independent Test**: Open the workspace agents page and an agent's form: name and role are editable, key is displayed read-only; save a rename and confirm the key is unchanged. Trigger a Jira-visible event (e.g. a run comment) and confirm the agent is presented as "name (role)".

**Acceptance Scenarios**:

1. **Given** the workspace agents list and agent form, **When** an agent is displayed, **Then** the persona name and role are shown and editable, and the key is shown as a read-only technical identifier.
2. **Given** an agent create from the dashboard, **When** the form is submitted with name + role, **Then** the key is generated server-side and returned in the response; the client cannot set it.
3. **Given** human-facing generated text (Jira comments, reconcile/status messages), **When** an agent is mentioned, **Then** it is presented as "name (role)" (or by key where a technical handle is more appropriate, e.g. logs), never as a bare ambiguous name.

### User Story 4 - Existing data migrates safely (Priority: P1, ships with Story 1)

Existing agent rows (including every workspace's seeded orchestrator and the current test workspace whose agents are named like "st3-developer") gain `role` and `key` values via a deterministic backfill, with uniqueness guaranteed, so the system upgrades in place with zero manual fixes and no behavior change for in-flight runs.

**Why this priority**: The schema change cannot ship without it — `key` is NOT NULL.

**Independent Test**: Apply the migration to a database containing pre-feature rows (workers + orchestrators, including name collisions after slugging) and verify every row has a non-empty unique key, orchestrators have role "teamlead" and the reserved key, and no run/human-task references broke.

**Acceptance Scenarios**:

1. **Given** a pre-feature agent row, **When** the migration runs, **Then** `key` = the canonical slug of its current name (role is unknown at backfill time and left null for workers), and `(workspace_id, key)` uniqueness is enforced with `-2`/`-3` suffixes on collision.
2. **Given** a workspace's seeded orchestrator row, **When** the migration runs, **Then** it receives role "teamlead" and the reserved orchestrator key, and orchestrator seeding/lookup no longer depends on the name column.
3. **Given** in-flight runs and human tasks referencing agents by id, **When** the migration runs, **Then** those references are untouched and resume paths continue to work.

### Edge Cases

- **Key collision within a workspace** (two personas slugging to the same key, or a re-created agent reusing a retired persona): system appends the smallest free numeric suffix (`-2`, `-3`, …). Applies identically at generation, admin-plane creation, dashboard creation, and backfill.
- **Empty slug** (persona name in non-Latin script or all symbols, e.g. "Ахиллес"): deterministic fallback chain — slug of role alone; if that is also empty, a generic stem (e.g. `agent`) — then normal collision suffixing. A key is never empty.
- **Routed target key unknown, disabled, or pointing at the orchestrator itself**: escalate to a human task exactly as today's unknown-target handling; never route by fuzzy match on name.
- **Attempt to change key via update** (dashboard PATCH, admin-plane update): the key field is not accepted by update contracts; if supplied it is rejected or ignored (decide one behavior and test it) — the stored key never changes.
- **A worker created with the reserved orchestrator key's name/role combination** (e.g. persona "Brigadir", role "teamlead" → slug `brigadir-teamlead`, or a name slugging to `brigadir`): the reserved key is excluded from derivation results; collision suffixing produces `brigadir-2` etc., so no worker can ever hold the orchestrator's key.
- **Concurrent creation racing on the same key**: the database uniqueness constraint is the final arbiter; the create path retries with the next suffix rather than failing the whole operation.
- **Name/role edits during an active run**: safe by construction — runs and tasks reference agents by id; the roster is re-rendered per handoff, so the orchestrator always sees current keys.
- **Duplicate persona names in one workspace**: allowed (uniqueness on name is dropped); human-facing text disambiguates via "name (role)" and the UI shows the key.

## Requirements *(mandatory)*

### Functional Requirements

**Identity model**

- **FR-001**: Each agent MUST carry three identity-adjacent fields: `id` (existing immutable internal identity), `name` (editable persona display name, no uniqueness constraint), and `key` (readable handle, NOT NULL, unique per workspace, immutable after creation). A new free-text `role` field describes the agent's function (e.g. Developer, QA, Reviewer, Planner; orchestrator = "teamlead").
- **FR-002**: The former uniqueness constraint on (workspace, name) MUST be dropped; the new uniqueness constraint is on (workspace, key).
- **FR-003**: ALL persisted and internal references, joins, lookups, and conflict targets MUST use `id`. After this feature, no code path may use the agent name as an identifier. A full audit of existing name-as-identity usages (routing resolution, orchestrator seed lookup/on-conflict, team validation, any others found by scan) is part of the feature's definition of done.
- **FR-004**: `key` MUST appear ONLY at boundaries where the handle passes through an LLM or is shown to a human: the orchestrator's roster, the routed-outcome target field, URLs, logs, and UI. Wherever a key enters the system it MUST be resolved to `id` immediately at that boundary; keys are never stored as long-lived references.

**Key derivation**

- **FR-005**: There MUST be exactly ONE canonical slug function for agent keys in the shared contracts layer, with the rule: concatenate name and role, lowercase, replace every character outside [a-z0-9] with `-`, collapse repeated `-`, trim leading/trailing `-` ("Hera" + "Reviewer" → `hera-reviewer`). All creation paths use this one function; no second implementation may exist.
- **FR-006**: The system MUST generate the key exactly once, at agent creation, on every creation path (in-run team apply, admin-plane create-agent/create-team/generate-agents, dashboard create, orchestrator seeding, migration backfill). The key MUST never be accepted from an LLM or an API client.
- **FR-007**: Agent update paths MUST NOT modify the key — not on name change, not on role change, not when a key value is supplied in the payload.
- **FR-008**: On key collision within a workspace, the system MUST append the smallest free numeric suffix (`-2`, `-3`, …). If derivation yields an empty slug, the system MUST fall back deterministically (role-only slug, then a generic stem) before suffixing. The database uniqueness constraint remains the final guard; creation retries on constraint violation.

**Routing**

- **FR-009**: The orchestrator roster in the handoff MUST list each enabled non-orchestrator worker's key, name, role, and description, and the handoff prose MUST instruct routing by key.
- **FR-010**: The routed outcome's target field is semantically the target worker's key. The system MUST resolve it against enabled non-orchestrator workers of the workspace by exact key match and continue by id. An unknown, disabled, or orchestrator-targeting key MUST escalate to a human task (unchanged unknown-target behavior); no fuzzy or name-based matching.

**Team generation**

- **FR-011**: Team generation (both the admin-plane generate flow and the in-run setup proposal) MUST instruct the model to invent ONE coherent random theme per workspace and assign every proposed agent a themed persona name plus a functional role. The product MUST NOT hardcode a list of themes; theme variety comes from the model.
- **FR-012**: Team proposals from the model MUST carry name + role only (plus existing fields like description); keys are absent from the model-facing contract. Team validation MUST enforce uniqueness on derived keys (post-suffixing this always succeeds; validation guards persona-name-set degenerate cases such as an entire team slugging to one key) and persona names within one proposed team SHOULD be distinct.

**Orchestrator**

- **FR-013**: The seeded orchestrator MUST have role "teamlead" and the reserved key `brigadir`. Seeding singleton lookup and insert-if-absent conflict handling MUST key on the orchestrator flag / (workspace, key) — never on name. The orchestrator's persona name remains editable like any other agent's.
- **FR-014**: The key `brigadir` is reserved per workspace: no worker creation path may produce it (collision suffixing applies), and routing to it escalates per FR-010.

**Surfaces**

- **FR-015**: Dashboard agent read contracts MUST expose id, key, name, and role. Create accepts name + role and returns the generated key; update accepts name/role edits and cannot change the key.
- **FR-016**: The workspace agents UI MUST show persona name and role as editable fields and the key as a read-only technical identifier, on both the list/card and the form.
- **FR-017**: Human-facing generated text that mentions an agent (Jira comments, reconcile/status messages) MUST present it as "name (role)" — or the key where a technical handle fits better (logs) — never a bare name.
- **FR-018**: The admin-plane tool contracts (create_agent, create_team, generate_agents) MUST accept name + role and never accept or emit a caller-supplied key; responses include the system-generated key.

**Migration & invariants**

- **FR-019**: A committed migration MUST add `role` (nullable text) and `key` (NOT NULL text) with the (workspace, key) unique constraint, drop the (workspace, name) unique constraint, and deterministically backfill existing rows: workers get key = canonical slug of current name with role left null; orchestrators get role "teamlead" and key `brigadir`; collisions get numeric suffixes. The documented schema (architecture doc §3) MUST be updated in the same change.
- **FR-020**: name, role, and key are presentation/handle concerns only: they MUST NOT influence the run status machine, Jira transitions, idempotency keys, or completion semantics. Existing invariants (system-only Jira writes, id-based human-task/resume references) are unchanged and MUST be verified by the audit.
- **FR-021**: Tests MUST ship in the same iteration covering at minimum: the slug rule (incl. empty-slug fallback and collision suffixing), key generation on every creation path, key immutability on update, workspace-scoped uniqueness, routed key→id resolution incl. unknown/disabled/reserved targets, both team-creation paths (in-run apply and admin plane), orchestrator seeding by flag/key, and the backfill migration against pre-feature data.

### Key Entities

- **Agent**: an orchestrated worker (or the per-workspace orchestrator). Identity: `id` (immutable UUID, all internal references). Handle: `key` (immutable readable slug, unique per workspace, LLM/human boundary only). Presentation: `name` (editable persona, non-unique) and `role` (editable free-text function; "teamlead" for the orchestrator). All other attributes unchanged.
- **Team proposal**: a model-produced set of agent drafts (name, role, description, …) under one workspace theme; contains no keys — the system derives them on apply.
- **Routing decision**: the orchestrator's "routed" outcome; its target field carries a worker key that the system resolves to an agent id at the boundary.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of routed decisions naming a valid roster key start a rework run for exactly that agent; 100% of decisions naming an invalid key escalate to a human task. Zero misroutes attributable to renames or duplicate persona names.
- **SC-002**: Renaming an agent's persona or role never changes its key, breaks an in-flight run, a human task, or a historical reference — verifiable by editing an agent mid-run with zero resulting errors.
- **SC-003**: Two agents in one workspace can share a persona name with no save errors and no ambiguity in routing or internal references.
- **SC-004**: Team generation on distinct workspaces produces themed persona names with roles, coherent within each workspace; all keys system-derived, non-empty, and unique — with no theme list present in the product itself.
- **SC-005**: The migration backfills 100% of existing agent rows to non-empty, workspace-unique keys (orchestrators: role "teamlead", key `brigadir`) with zero manual fixups and zero broken references.
- **SC-006**: A codebase audit finds zero remaining uses of the agent name as an identifier (lookup, join, conflict target, dedup key).

## Decisions Proposed *(from the open questions in the input)*

1. **Orchestrator key = `brigadir` (not `brigadir-teamlead`), reserved.** Justification: it is the product's own persona and the shortest stable handle for logs/URLs; the role is already carried by the separate `role` field ("teamlead"), so encoding it in the key duplicates data the key must never track (key is immutable, role is editable). Reservation is required: the orchestrator is excluded from routing targets, so its key must be impossible for a worker to acquire (FR-014).
2. **Theme selection is fully delegated to the model — no theme list in code.** Justification: any hardcoded list caps variety at the list's size and defeats "different every workspace"; the generation prompt instructs "invent ONE coherent theme" and the examples in the prompt are illustrative, not enumerable options. Uniqueness is enforced structurally (distinct personas per team; system-side key suffixing), not by constraining the theme.
3. **Test-workspace backfill is deterministic, regeneration optional.** Justification: the migration must be safe and unattended (Constitution: migrations committed and reviewed), so existing rows like "st3-developer" get key = `st3-developer`, role = null — no data invented in SQL. Re-theming that team is a one-command follow-up through the admin-plane generate flow after the feature ships, not a migration concern.

## Assumptions

- `role` is free text, not an enum — the theme-driven generation and human editing need latitude; "teamlead" is the only value with system meaning (orchestrator), and even that is carried by the existing orchestrator flag, not by parsing the role.
- Backfilled workers get role = null (the current names like "st3-developer" encode a function, but parsing it in a migration is guesswork; null is honest and editable later). Nothing in the system requires a non-null role.
- The routed-target field name in the report contract stays as-is (`target_agent`), reinterpreted as carrying the key; no parallel field is introduced. Pre-feature keys equal old slugged names, so historical reports remain readable.
- Key immutability is absolute in this feature — there is no admin "regenerate key" escape hatch. If a persona change makes a key misleading, the remedy is delete + recreate (acceptable for an internal tool).
- URLs/logs may adopt the key opportunistically where agents are referenced; no exhaustive URL-scheme redesign is in scope.
- Uniqueness of persona names within one generated team is a quality expectation on generation (SHOULD), not a database constraint — the key carries the hard uniqueness.
