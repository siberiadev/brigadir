## Ввод

```text
$ARGUMENTS
```

Из ввода нужен **run id** — UUID из `…/runs/<uuid>` или сам UUID. Если ввод пуст или UUID не
извлекается — спроси ссылку и остановись. Если приложена ссылка на коммит/MR — это артефакт
прогона, его надо верифицировать (шаг 4).

## Что делает этот скилл

Разбирает один прогон и производит **один файл** `docs/runs/<YYYY-MM-DD>-run-<short-id>-<slug>.md`
с: фактами прогона, независимой проверкой того, что агент утверждает, предложениями по улучшению
**платформы** (не тикета), а если прогон не `succeeded` — планом разблокировки/перезапуска.

Ключевой принцип: **отчёт агента — это заявление, а не факт.** Всё, что можно проверить дёшево
(строки в файлах, наличие коммитов, зелёность гейта, статус тикета), проверяется против реального
дерева и БД. Утверждение, которое не удалось проверить, помечается как непроверенное — не как
подтверждённое.

Второй принцип: рекомендации — **о платформе**. Вывод «агент плохо написал summary» бесполезен;
вывод «лимит `summary` не объявлен в описании тулзы, поэтому 4 из 5 вызовов `complete_task`
отклонены» — полезен, потому что чинится в коде brigadir. Каждая рекомендация должна быть
привязана к `file:line` в этом репозитории.

## Шаг 0. Доступ

Токен и API — из `.env` в корне репозитория:

```bash
set -a; source .env; set +a
API=${BRIGADIR_API_URL:-http://localhost:3000}
AUTH="Authorization: Bearer $BRIGADIR_DASHBOARD_TOKEN"
```

Если бэкенд не поднят — все запросы отдадут connection error. Скажи об этом и предложи
`docker compose up` или `pnpm dev` (см. `docs/local-setup.md`); не пытайся читать данные
из БД в обход API, кроме случаев из шага 2.

Прямой доступ к БД как fallback (когда нужен столбец, которого нет в API):
`psql "postgres://brigadir:brigadir@localhost:5434/brigadir"`. Полезное: у `tickets` статус
называется **`last_seen_status`** (не `status`), есть `blocked_by jsonb` и `blocked_state text`;
у `executors` нет `allowed_tools` — разрешённые тулзы лежат в `config` jsonb и в дефолтах
`libs/executors/src/claude-cli/claude-cli.config.ts`.

## Шаг 1. Собрать факты прогона

```bash
curl -s -H "$AUTH" "$API/api/runs/<run-id>" > /tmp/run.json
```

Ответ: `{ run, ticket, checks, artifacts, events, history }` (контракт —
`packages/contracts/src/runs.schema.ts`, эндпоинт — `apps/backend/src/dashboard/runs.controller.ts:255`).

Вытащи и зафиксируй:

- `run.status` (`queued` | `running` | `awaiting_human` | `succeeded` | `failed` | `cancelled` |
  `timed_out` | `superseded`), `run.outcome`, `run.attempt`, `run.error`.
- `run.duration_ms`, `run.cost_usd`.
- `run.usage`: `output_tokens`, `input_tokens`, `cache_read_input_tokens`,
  `cache_creation_input_tokens`. Считай долю cache_read во вводе — она почти всегда >95 %, и это
  говорит, что стоимость определяется **числом round-trip'ов**, а не размером отдельного ответа.
- `run.agent` (name/key/role), `ticket.key`, `ticket.summary`, `run.workspace_id`.
- `checks[]` — заявленные гейты со статусами.
- `artifacts[]` — `{repo, branch, pr_url, commits_count, files_changed}`.
- `history[]` — все прогоны того же тикета: сколько попыток, кто до и после.

Профиль тулзов — из `events` (типы: `tool_call`, `progress`, `text`/`assistant`, `command`,
`log`, `error`, `api_retry`, `jira_action`, `system`):

```bash
python3 - <<'PY'
import json, collections, re
d = json.load(open('/tmp/run.json'))
ev = d['events']
print('events:', collections.Counter(e['type'] for e in ev))
tools = [e for e in ev if e['type'] == 'tool_call']
print('tools:', collections.Counter((e['payload'] or {}).get('name') for e in tools))
# Bash: сколько вызовов вообще ничего не меняют (значит, это была бы работа Read/Grep).
# Классифицируй по НАЛИЧИЮ изменяющей команды, а не по первому слову: реальные вызовы —
# это цепочки `cd X && sed … ; echo … ; ls …`, и префикс о смысле ничего не говорит.
bash = [(e['payload'] or {}).get('input', {}).get('command', '') for e in tools
        if (e['payload'] or {}).get('name') == 'Bash']
MUT = re.compile(r'\b(git (add|commit|push|checkout|switch|merge|fetch|pull|stash|worktree|reset)'
                 r'|npm|npx|pnpm|yarn|mkdir|mv|cp|rm|tee|touch|chmod|docker)\b')
ro = [c for c in bash if not MUT.search(c)]
cd = sum(bool(re.match(r'^\s*cd\s', c)) for c in bash)
print(f'bash={len(bash)} inspection-only={len(ro)} mutating={len(bash)-len(ro)} starts-with-cd={cd}')
PY
```

Смотри в этих числах на четыре вещи:

1. **Повторные вызовы одной тулзы подряд с одним смыслом** — почти всегда отклонение валидации.
   Особенно `complete_task`: несколько вызовов = агент бился о схему. Достань длины полей и
   сравни с лимитами `packages/contracts/src/report.schema.ts` (`summary` ≤ 2000, `checks` ≤ 50,
   `check.reason` ≤ 1000, `artifacts.repos` ≤ 20).
2. **`Bash` вместо `Read`/`Grep`** — чтение файлов через `sed`/`cat` делает таймлайн слепым
   (feature 026) и не дедуплицируется.
3. **Повторные `cd` в worktree** — следствие того, что CLI спавнится с `cwd: workspaceDir`
   (`libs/executors/src/claude-cli/claude-cli.executor.ts:562`), а shell-состояние между
   вызовами не живёт.
4. **`Skill` / `ToolSearch`, которые не сработали** — сверься с
   `DEFAULT_REPO_RUN_ALLOWED_TOOLS` (`claude-cli.config.ts`), чтобы отделить «не разрешено»
   от «не найдено».

## Шаг 2. Контекст вокруг прогона

```bash
# карточка workspace: репозитории, default_branch, env, настройки
curl -s -H "$AUTH" "$API/api/workspaces/<workspace-id>"
# человекозадачи этого workspace (open и closed) — ищи те, у которых run_id = наш прогон
curl -s -H "$AUTH" "$API/api/human-tasks?status=open&workspace=<workspace-id>&page_size=100"
curl -s -H "$AUTH" "$API/api/human-tasks?status=closed&workspace=<workspace-id>&page_size=100"
# история тикета: причинные связи, циклы доработки, вердикты оркестратора
curl -s -H "$AUTH" "$API/api/workspaces/<workspace-id>/tickets/<TICKET-KEY>/history"
# тикеты, ждущие блокеров
curl -s -H "$AUTH" "$API/api/workspaces/<workspace-id>/waiting"
# инструкция агента, который делал прогон
curl -s -H "$AUTH" "$API/api/agents?workspace=<workspace-id>&page_size=100"
```

Что здесь важно:

- **`repositories[].default_branch`** — стартовая точка worktree
  (`libs/executors/src/claude-cli/worktree.ts:229`, `git worktree add --detach` от
  `origin/<default_branch>`). Если она не та, что подразумевает инструкция агента, прогон стартовал
  не оттуда, откуда все думают.
- **Человекозадачи с `run_id` нашего прогона** — читай `title`/`details` и проверяй, правда ли
  сказанное. Задачи вида `[blocker_branch_lost]` / `[blocker_no_artifact]` порождаются
  `applyMissingBranchMatrix` (`claude-cli.executor.ts:1300+`) на основе БД, **не** глядя в git —
  они бывают ложными. Проверить дёшево: `git log --grep=<blockerKey>` в стартовой точке.
- **Инструкция агента против wrapper'а.** Wrapper
  (`libs/executors/src/claude-cli/wrapper.ts`, `repositoriesSection()`) диктует свою модель
  ветвления/PR. Если инструкция агента говорит другое (например «общая эпик-ветка, никаких PR»),
  зафиксируй противоречие: агент получает два конфликтующих текста, и то, что он выбрал верный, —
  везение, а не гарантия.

## Шаг 3. Прочитать таймлайн целиком

Не полагайся на агрегаты. Прочитай `progress`-события и `text`/`assistant`-фрагменты в порядке
времени — там видны формулировки, по которым понятно, **где агент тратил время на разведку
платформы вместо задачи**: «которая директория рабочая», «где лежит план», «сколько символов
можно в summary», «почему скилл не запустился». Каждый такой момент — кандидат в рекомендацию:
это факт, который платформа могла сообщить в промпте бесплатно.

Также обрати внимание на `error` и `api_retry` события: rate-limit'ы и ретраи API — это
не вина агента, но они удлиняют прогон и попадают в стоимость.

## Шаг 4. Верифицировать утверждения (обязательно)

Возьми `summary`, `checks` и артефакты и проверь их против реальности. Это ядро анализа —
без него документ становится пересказом отчёта агента.

- **Коммиты и дифф.** Найди локальные клоны целевых репозиториев (`find ~ -maxdepth 4 -name
  <repo-name> -type d` — пути редко там, где кажется). Затем: существуют ли заявленные коммиты,
  на той ли ветке, тот ли префикс `<KEY>:` в сообщении, столько ли файлов.
  ```bash
  git -C <repo> fetch origin
  git -C <repo> log --oneline --grep=<TICKET-KEY> origin/<branch>
  git -C <repo> show --stat <sha>
  git -C <repo> show "<sha>:<path>"   # кавычки обязательны: zsh ломает rev:path
  ```
- **Построчные цитаты.** Если артефакт (spec/plan/tasks, ревью, отчёт) ссылается на `file:line` —
  проверь, что там действительно то, что заявлено. Расхождение цитат — сигнал, что цитаты в
  артефактах никем не верифицируются.
- **Числовые/поведенческие утверждения.** Если агент утверждает эквивалентность, идентичность
  метрик, отсутствие паттерна — воспроизведи проверку (`grep -c`, крошечный `node -e` скрипт на
  диапазоне входов). Именно здесь обнаруживаются и настоящие находки агента, и его выдумки.
- **Гейты.** `check.status: pass` без соответствующей команды в `events` — заявление без
  доказательства. Отметь это; повторяющийся паттерн = нужна платформенная проверка
  «pass без исполненной команды».
- **Jira.** Читай статусы через Atlassian MCP (read-only). **Никогда не пиши в Jira** — ни
  комментарий, ни транзишн: в Jira пишет только система (правило проекта).

Результат шага — таблица «утверждение → проверка → ✅/❌/не проверено».

## Шаг 5. Если прогон не `succeeded` — план разблокировки

Диагноз зависит от статуса. Не предлагай перезапуск, пока не назвал причину.

**`awaiting_human`** — прогон запаркован, его нельзя «оживить» перезапуском.
1. Найди человекозадачу этого прогона (шаг 2), прочитай `title`, `details`, `options`, `blocking`.
2. Определи, **настоящий** ли это вопрос или артефакт платформы (ложные `blocker_*`-задачи, см.
   шаг 2). Ложную — закрывать `dismiss` и заводить рекомендацию по исправлению генератора.
3. Настоящий вопрос — сформулируй ответ и рекомендуемую опцию, но **решение остаётся за
   человеком**. Команда разблокировки:
   ```bash
   curl -s -X POST -H "$AUTH" -H 'Content-Type: application/json' \
     -d '{"action":"resume","answer":"<ответ ≤4000 симв>","resolved_by":"<кто>"}' \
     "$API/api/human-tasks/<task-id>/resolve"
   ```
   `action`: `resume` (продолжить, attempt+1) · `done_manually` (человек сделал сам) ·
   `dismiss` (снять). Опционально `target_agent_id` — передать другому **enabled** агенту того же
   workspace (feature 010). Контракт — `packages/contracts/src/resolve-human-task.schema.ts`,
   эндпоинт — `libs/human-tasks/src/resolve.controller.ts:26`.
   Ответ `409 not_open` = задача уже закрыта или прогон больше не `awaiting_human`.

**`failed`** — сначала отдели три причины:
- *реальный провал работы* (гейт красный, критерий не выполнен) → нужен новый прогон с исправленным
  входом: уточнить тикет / план / инструкцию, и только потом retry;
- *провал среды* (нет БД, нет креды, `npm ci` упал, порт занят) → чинить окружение, retry без
  изменений в тикете. Проверь `env` в карточке workspace и слои env (workspace < repo < agent,
  feature 031);
- *провал платформы* (агент не смог отчитаться, схема отклонила отчёт, тулза не разрешена,
  таймаут воркера) → это баг brigadir, и он идёт в рекомендации, а не в retry.

Перезапуск (идёт через тот же manual-trigger, все три уровня дедупа целы —
`runs.controller.ts:443`):
```bash
curl -s -X POST -H "$AUTH" "$API/api/runs/<run-id>/retry"
```
`409 active_run_exists` = по этому тикету+агенту уже есть активный прогон (partial unique index
`runs_one_active`); сначала посмотри, какой, и не отменяй его вслепую.

**`timed_out`** — посмотри `run.error`: там сохраняются последние ≤16 КБ вывода (инцидент
2026-07-19). Отдели «агент работал и не успел» от «агент завис на одной команде». Для первого
случая рекомендация — поднять лимит времени агента или раздробить тикет; для второго — найти
команду (обычно долгий тест-сьют или интерактивный процесс) и назвать её. Retry тем же вызовом,
что выше, но только после того, как причина устранена: повтор с тем же лимитом даст тот же таймаут.

**`cancelled`** — кто отменил: одиночный `cancel`, `cancel-all` по workspace, или это следствие
паузы. Отмена ничего не ломает; retry достаточно.

**`superseded`** — прогон вытеснен более новым. Смотри `history` — работай с актуальным прогоном,
этот разбирать бессмысленно, кроме случая, когда вытеснение само было ошибкой.

**`queued` / `running` дольше ожидаемого** — не пиши post-mortem незакончившегося прогона.
Проверь, поднят ли воркер, и совпадает ли `BULLMQ_PREFIX` (правило #6: изоляция неймспейсами,
`flushdb` на общем redis сносит живые джобы соседа). Скажи, что прогон ещё идёт, и остановись.

**Все команды, меняющие состояние (`resolve`, `retry`, `cancel`), — только с подтверждения
пользователя.** Выведи готовую команду и скажи, что она сделает; не выполняй сам без «да».
Никаких деструктивных git-команд ни при каких условиях (`push --force`, `reset --hard`,
`branch -D`, `clean -f`, `rebase` на общей ветке) — предлагай `git revert` / `git stash` /
backup-ветку.

## Шаг 6. Написать файл

Путь: `docs/runs/<YYYY-MM-DD>-run-<первые-8-символов-run-id>-<короткий-слаг>.md`, дата — сегодняшняя.
Каталог `docs/runs/` уже существует; если нет — создай. Один прогон = один файл; существующие
файлы не перезаписывай.

Структура (порядок обязателен, пустые секции опускай):

```markdown
# Разбор прогона <short-id> — <Agent> / <TICKET-KEY> (<роль/стадия>)

**Дата:** … · **Прогон:** `<uuid>` · **Агент:** … · **Тикет:** … · **Исход:** <status/outcome>, <длительность>, <$>
**Артефакт:** <коммит/ветка/MR, если есть>

<1–3 строки: что это был за прогон и почему он разбирается>

## 1. Что прогон сделал <хорошо | и на чём встал>
<таблица «утверждение → проверка», затем настоящие находки агента или настоящая причина провала>

## 2. Измерения
<блок кода: duration, cost, токены, профиль тулзов, доля read-only Bash, повторные вызовы>

## 3. Предложения по улучшению brigadir
### 3.N <заголовок>
**Наблюдение.** <факт с числами из этого прогона>
**Причина.** <механика, с `file:line` в brigadir>
**Предложение.** <что поменять; помечай гипотезы гипотезами>
**Эффект.** <что конкретно экономится или перестаёт ломаться>

## 4. Разблокировка / перезапуск   ← только если прогон не succeeded
<диагноз по шагу 5, готовые команды, что нужно поменять ДО перезапуска>

## 5. Приоритеты
<таблица: улучшение | стоимость | отдача — отсортированная по отношению отдачи к стоимости>

## 6. Что не требует изменений
<что сработало — чтобы это не «починили» в следующий раз>
```

Требования к содержанию:

- **Каждое наблюдение — с числом или цитатой** из этого прогона. «Агент много читал файлов» —
  плохо; «42 из 56 Bash-вызовов были `sed`/`grep`/`cat`» — хорошо.
- **Каждая причина — с `file:line`** в brigadir. Если механика не найдена — пиши
  «гипотеза, требует проверки» и назови, каким экспериментом она проверяется.
- **Не выдумывай метрики.** Чего нет в `usage`/`events` — того нет в документе.
- **Секция 6 обязательна.** Post-mortem без неё провоцирует ломать работающее.
- **Русский язык**, как в остальных `docs/`; идентификаторы, пути и команды — как есть.
- Не редактируй `docs/progress.md`, `docs/plan-internal.md` и прочие документы-источники правды:
  этот скилл производит только файл в `docs/runs/`.

## Шаг 7. Ответить пользователю

В чате: путь к файлу, 3–5 главных выводов с числами, и — если прогон не `succeeded` — что именно
надо сделать, чтобы его разблокировать, с готовой командой. Не пересказывай весь документ.

## Повторяющиеся находки (проверяй в первую очередь)

Прежде чем «открывать» проблему, посмотри существующие файлы в `docs/runs/` — возможно, она уже
описана, и правильный вывод «воспроизвелось снова, N-й раз», а не новая рекомендация. Известные
классы:

1. **Лимиты схемы не объявлены агенту** — `packages/mcp-server/src/main.ts` описывает
   callback-тулзы без числовых границ, границы живут в `packages/contracts/src/report.schema.ts`.
   Симптом: несколько `complete_task` подряд.
2. **`cwd` спавна = workspace-корень** (`claude-cli.executor.ts:562`) — симптомы: повторные `cd`,
   не найденные repo-local `.claude/skills`, «не там запустил команду».
3. **`Bash` вместо `Read`/`Grep`** — таймлайн (feature 026) перестаёт быть читаемым.
