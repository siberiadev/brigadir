## 3. Предложения по улучшению brigadir

### 3.1 Лимит `summary` не сообщён агенту заранее — 4 лишних round-trip'а

**Наблюдение.** `complete_task` вызывался 5 раз. Длины `summary`: 3320 → 2711 → 2477
→ 2326 → 1971 символов. Первые четыре отклонены по `ReportSchema.summary.max(2000)`
(`packages/contracts/src/report.schema.ts:167`). В таймлайне видно, как агент это
осознаёт: progress-событие «The summary needs to fit 2000 characters. Trimming.»

**Причина.** Описание тулзы (`packages/mcp-server/src/main.ts:82`) — одна строка:
«Finish the run with a structured report (outcome, summary, checks, optional artifacts).
The single normal way to end a session.» Ни лимита, ни намёка на него. Агент узнаёт
о границе только из текста ошибки валидации.

**Предложение.**
- Вписать лимиты в `description` тулзы и в `.describe()` полей схемы:
  `summary` ≤ 2000 симв., `checks` ≤ 50, `check.reason` ≤ 1000, `artifacts.repos` ≤ 20.
  Дешевле всего и почти наверняка убирает все 4 повтора.
- Дополнительно: возвращать в ошибке валидации фактическую длину и лимит
  («summary is 3320 chars, max 2000 — trim by 1320»), чтобы попытка была одна, а не
  четыре последовательных недо-обрезки.
- Стоит обсудить: не поднять ли сам лимит до ~4000 для планировщика. Первая версия
  (3320) содержала больше полезного, чем финальная (1971) — лимит здесь режет
  сигнал, а не шум. Мера безопасности от «стены текста» уже есть в
  `human_task.details` (4000).

**Эффект:** −4 round-trip'а с полным контекстом. При 6 МБ cache-read на прогон это
самая крупная одиночная экономия в этом прогоне.

### 3.2 `Skill` вызвался, но repo-local скиллы не подхватились

**Наблюдение.** `Skill` вызван один раз:
`{"skill": "speckit-specify", "args": "SXF-1174 … SPECIFY_FEATURE_DIRECTORY=specs/SXF-1174-metrics-math-util"}`.
Не сработал. Check #9 агента: *«Followed .specify/ templates by hand — the /speckit-*
skills are repo-local .claude/skills and were not invocable via the Skill tool in this
session.»* Агент выехал на ручном следовании `.specify/templates/*` — результат по
структуре неотличим от настоящего, но это стоило токенов (несколько `sed -n` по
`SKILL.md` и шаблонам) и опирается на добросовестность модели.

**Причина (гипотеза, требует проверки).** `Skill` есть в
`DEFAULT_REPO_RUN_ALLOWED_TOOLS` (`claude-cli.config.ts:77`), то есть разрешение не
при чём. CLI спавнится с `cwd: workspaceDir` (`claude-cli.executor.ts:562`) — это
корень worktree, а `.claude/skills/` лежит на уровень глубже, в
`<workspaceDir>/squad-pulse-api/.claude/skills/`. Многорепозиторный layout ломает
обнаружение project-scoped скиллов.

**Предложение.**
- Проверить гипотезу: у одно-репового прогона (`cwd` == корень репо) скиллы должны
  подхватываться. Если так — при монтировании одного репозитория спавнить CLI с
  `cwd` = каталог этого репо, а не workspace-корень.
- Для многорепового случая: симлинковать/собирать `.claude/skills/` смонтированных
  репозиториев в workspace-корень при подготовке worktree (конфликты имён — по
  порядку монтирования, как у env).
- В любом случае: если репозиторий содержит `.claude/skills/` или `.specify/`,
  упомянуть это в `## Repositories` фактом («repo-local skills: speckit-*»), чтобы
  агент не тратил вызовы на разведку их существования.

### 3.3 68 % вызовов — `Bash`, и 51 из 56 ничего не меняют

**Наблюдение.** `Bash` 56 против `Read` 6, при этом изменяющих команд среди Bash всего 5.
Типичные вызовы: `sed -n '490,600p' src/boards/boards.service.ts`,
`grep -n … | head -40`, `sed -n … ; echo "=== … ===" ; ls …`. То есть `Read` с
`offset`/`limit` подменяется `sed`, а `Grep` — `grep | head`.

**Почему это плохо для платформы.** `tool_input-sanitizer` и таймлайн различают
структурные тулзы; `Bash` — чёрный ящик. Прочитанное через `sed` не видно как
«агент прочитал файл X строки N–M», а как строка команды. Для ревью прогона
(и для feature 026 «читаемый таймлайн») это потеря.

**Предложение.**
- В wrapper добавить одну строку в правила: «для чтения файлов используй `Read`
  (с `offset`/`limit` для длинных), `Grep`/`Glob` для поиска; `Bash` — для команд,
  которые действительно исполняют что-то (git, npm, node -e)». Это не про экономию
  токенов напрямую, а про наблюдаемость и меньшую вероятность обрезки вывода.
- Возможная экономия есть и в токенах: `sed -n '490,600p'` тянет 110 строк без
  нумерации и без учёта уже прочитанного; `Read` дедуплицируется харнессом.

### 3.4 20 повторных `cd` в worktree — cwd не переживает вызовы

**Наблюдение.** 19 из 56 `Bash`-команд начинаются с
`cd /Users/…/.brigadir/worktrees/5890636f-…/squad-pulse-api`. Агент вынужден
переустанавливать рабочий каталог, потому что shell-состояние между вызовами
не сохраняется, а спавн идёт в workspace-корень.

**Предложение.** Тот же фикс, что и 3.2: при одном смонтированном репозитории
спавнить с `cwd` внутри него. Для многорепового — явно сказать в wrapper, что
каждый `Bash` начинается в workspace-корне и cwd не сохраняется, чтобы агент
сразу писал `cd <repo> && …` одной строкой вместо двух вызовов. Экономия ~20
префиксов по ~90 символов — мелочь в токенах, но убирает класс ошибок «команда
выполнилась не в том каталоге».

### 3.5 Ложная human-task от матрицы наследования

**Наблюдение.** Заведена задача
`[blocker_branch_lost] SXF-1174: no usable branch from SXF-1173 for this run's repositories`
с текстом *«SXF-1173 is still open (status unknown) but left no usable branch — starting
from the default branch WITHOUT its work»*. Всё это неверно: SXF-1173 в `QA Done`,
его работа влита в эпик-ветку (`f29c427` + merge `db8cdcc`), и прогон стартовал именно
оттуда — следующая строка лога: `starting from feat/SXF-1172-board-metrics-dedup`.

**Причина.** Две подсистемы по-разному понимают «релиз блокера»:
- `dependency-gate.ts:47` уважает `dependency_release_status` — в логе есть
  `Released early: blocker(s) [SXF-1173] reached "QA Done" without being done`.
- `applyMissingBranchMatrix` (`claude-cli.executor.ts:1310`) проверяет только
  `category === 'done'`. `QA Done` имеет категорию `indeterminate`, поэтому вместо
  тихой ветки `blocker_branch_merged` срабатывает громкая `blocker_no_artifact`.

Плюс `statusName` не подставился («status unknown») — `fetchBlockerStatuses` кладёт
`name|category`, а `dropped` для `reason: no_artifacts` собирается отдельной ветвью,
где статус, судя по выводу, теряется.

**Предложение.**
- Передавать `dependency_release_status` workspace'а в `applyMissingBranchMatrix` и
  считать блокер «отпущенным» по тому же правилу, что и гейт: `category === 'done'`
  **или** имя статуса совпало. Иначе конфигурируемый порог (feature 032) работает
  в половине системы.
- Отдельно: перед тем как заявить «starting from X WITHOUT its work», можно
  дёшево проверить `git log --grep=<blockerKey>` в стартовой точке. Если коммиты
  блокера там есть — это `blocker_branch_merged` (тихо), а не человекозадача. Сейчас
  система утверждает факт о содержимом git, ни разу в git не посмотрев.
- Починить подстановку `statusName` в сообщении.

### 3.6 Артефакты плана некуда положить, кроме репозитория

**Наблюдение.** spec/plan/tasks (796 строк) лежат в коммите на эпик-ветке. Это
работает, но: (а) шумит в diff'е ветки, на которой ревьюят код; (б) следующая

у Odin выглядит как «планировщик менял репозиторий», хотя он менял только документы.

**Предложение (к обсуждению, не срочно).** Дать отчёту опциональное поле вида
`artifacts.docs: [{repo, path}]`, чтобы платформа знала путь к артефактам стадии и
могла подставить его в prompt следующей стадии фактом: «Plan for this ticket:
`specs/SXF-1174-metrics-math-util/` (from run …)». Это убирает разведку у Thor'а и
отделяет «изменил код» от «положил документы».
