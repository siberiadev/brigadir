# BRIGADIR — Рабочий план (внутренний инструмент)

**Это актуальный план работ.** Продукт строится как некоммерческий внутренний инструмент для своей команды. Полный roadmap продукта ([roadmap.md](roadmap.md)) и разделы Phase 2+ в [spec.md](spec.md) — справочный материал «на вырост»; при противоречии приоритет у этого файла.

## Принятые решения (2026-07-10)

1. **Подключение Jira — API token, без OAuth.** В форме создания workspace пользователь вставляет URL сайта + email + API-токен (создаётся на id.atlassian.com); система сразу валидирует его `GET /myself` и читает проект. Храним `expires_at` (токен живёт ≤ 1 года) и предупреждаем заранее. OAuth 3LO с редиректом — возможное будущее улучшение, не в плане.
2. **UI для workspace и агентов — с самого начала** (перенесено из Phase 2 в Phase 1): агентов будет создавать команда, а не один человек. Флоу: создать workspace (визард с подключением Jira, переподключение — в настройках) → внутри workspace список агентов, «+» создаёт агента (имя, инструкция, executor/модель, триггер-статус, целевые статусы).
3. **В Jira пишет только система.** Агент никогда сам не двигает карточку и не комментирует — он репортит через тулзы (`report_progress` / `request_human` / `complete_task`), а BRIGADIR переводит статусы, пишет комменты и создаёт задачи людям. Это правило зашито в обёртку инструкций.
4. **UI-библиотека — Element Plus** (Vue 3 + Vite + Pinia + TanStack Query): самый полный набор admin-компонентов под наши экраны и самая предсказуемая для агентной генерации кода. **Своей kanban-доски НЕТ** (решение 2026-07-11): Jira остаётся единственной доской — рисовать её read-only копию дорого и бессмысленно. Вместо неё вкладка **Runs** внутри workspace: список прогонов с фильтрами по агенту/статусу и поиском по ключу тикета.
5. **Workspace привязывается к Jira-борде, скоуп зависит от её типа** (решение 2026-07-11). При создании workspace указывается board id (или URL борды); система через Agile API (`GET /rest/agile/1.0/board/{id}`) валидирует борду и определяет тип. **Kanban** → в скоупе все задачи борды. **Scrum** → в скоупе только задачи **активного спринта** (`sprint in openSprints()`); нет активного спринта — поллер вхолостую, триггеры не срабатывают. Вход тикета в скоуп (старт спринта, добавление в активный спринт) эквивалентен смене статуса: если тикет вошёл в скоуп уже находясь в триггер-статусе агента — агент запускается. Старт нового спринта не трогает `updated` у задач → поллер отслеживает id активного спринта и при его смене делает полный рескан спринта в обход high-water mark.

Модель исполнения (подтверждена): один прогон агента = один процесс `claude -p` от начала до конца (внутренний цикл агент крутит сам, «итерации» снаружи не нужны); цепочка агентов — через статусы Jira (агент A завершился → система перевела тикет → новый статус триггерит агента B); агенты друг друга не запускают.

## Что вырезано из полного плана

- Executor'ы `anthropic_api` и `deepseek_api` — абстракция `AgentExecutor` остаётся в коде, реализации добавим при необходимости. Стартуем с `claude_cli` (+ опционально `claude_routines`).
- OAuth 3LO, динамические вебхуки, Forge — токен + поллинг (+ опционально один системный вебхук, если есть админ-права).
- Песочницы (Docker/gVisor), секрет-брокер с egress-прокси — доверенная команда: bare process + git worktree + env-санация.
- Multi-tenant, users/RBAC/SSO, биллинг, аудит, Marketplace — не нужны. Доступ к дашборду — один общий bearer-токен.
- Компилятор behavior→wrapper — один захардкоженный шаблон обёртки; behavior-опции добавим, если реально понадобятся.

## Итерации

Ритм работы: итерация = 0.5–2 дня, размер PR. Каждая: plan mode → одобрение плана (≈5 мин) → автономная реализация с тестами → чекпоинт по DoD. Журнал прогресса — `docs/progress.md` (ведётся автоматически с первой итерации).

| # | Итерация | Содержание | Участие пользователя |
|---|---|---|---|
| 1 | Скелет | Монорепо (backend/worker/contracts), Postgres-миграции, BullMQ-очереди, mock-executor, тесты пайплайна | Одобрить план, взглянуть на схему БД |
| 2 | Jira-ядро | JiraModule (token auth, rate-limiter, per-issue write queue, transition discovery, ADF), поллер `/search/jql` + high-water mark, машина статусов на mock'е | Тестовый Jira-проект + бот-аккаунт + токен |
| 3 | claude_cli | Executor: spawn `claude -p` (stream-json, `--json-schema`, лимиты, kill process group), env-санация, rate-limit-обработка | 15 мин: первый живой прогон на своей подписке |
| 4 | Callback + отчёты | MCP-сервер (3 тулзы), run JWT, ReportSchema, Stop-hook, скраббер секретов; обёртка обогащается контекстом фичи (эпик + linked issues) | Одобрить план |
| 5 | UI: workspace и агенты | Визард workspace (URL+email+токен, валидация `/myself`, чтение проекта, `expires_at`+алерт), CRUD агентов, переподключение Jira в настройках | Потыкать флоу создания |
| 6 | UI: Runs и human-queue | Вкладка Runs в workspace — список прогонов (фильтры: агент, статус прогона; поиск по ключу тикета; live-обновление через SSE), карточка прогона (чеклисты ✅/❌, таймлайн событий, стоимость, ссылка на Jira-тикет), страница Tasks с разрешением задач | Потыкать UI; критерий: боли №2 и №3 закрыты |

Обратная сторона принята осознанно: боль №1 (ненадёжная Jira Automation) живёт дольше, а обёртка/executor до внедрения обкатываются только на live-smoke и тестовых прогонах.

## Модель «временная команда под фичу» (анализ 2026-07-11)

Workspace + agents + scope_jql = временная команда digital employees на узкий список задач. Ядро дизайна модель поддерживает; выявленные пробелы и их размещение:

| Пробел | Решение | Итерация |
|---|---|---|
| Зависимости тикетов (frontend ждёт backend) | **Dependency gate**: триггер не срабатывает при незакрытых `is blocked by`; reconcile перепроверяет пропущенные (закрытие блокера не обновляет `updated`) — см. spec §0.4 | 2 (gate) |
| Контекст между агентами фичи | Обёртка включает эпик + linked issues со статусами/ветками/PR из отчётов прошлых прогонов | 4 (callbacks/обёртка) |
| Пауза/архив временной команды | `workspaces.enabled` — выключатель поллера с сохранением истории | 5 (UI) |
| Бюджет команды | Потолок/алерт стоимости на workspace (поверх per-run) | 6 (UI/stats) |
| Шаблоны команд | Экспорт/импорт набора агентов (yaml уже есть как основа) | 8+ |
| Финиш фичи = merge PR'ов | `code_delivery=pull_request` → non-blocking human task `kind=review`; merge — за человеком | 4 (callbacks) |

Не делаем осознанно: агент-декомпозитор (эпик→тикеты), мульти-репо в одном прогоне (split на тикеты + dependency gate покрывают кейс).

### Пост-MVP: админский MCP-сервер «Claude-тимлид» (идея 2026-07-11, итерация 8+)

Stdio MCP-сервер поверх админского API платформы, подключаемый к Claude Code. Сценарий: пользователь даёт Клоду ссылки на репозитории и Jira-борду и просит «собери команду под эти задачи»; Клод как тимлид смотрит задачи на борде, создаёт workspace и собирает в нём агентов под конкретный набор задач (триггер-статусы, инструкции, scope_jql).

- **Тулзы (эскиз)**: `inspect_board` (тип борды, статусы, задачи со статусами/линками — read-only разведка), `create_workspace` (борда + репозитории + scope_jql — та же валидация, что у визарда), `create_agent` / `update_agent`, `list_workspaces`, `export_team` / `import_team` (шаблоны команд из строки выше — yaml как формат обмена).
- **Не путать с callback-MCP итерации 4**: тот — для агентов ВНУТРИ прогона (report_progress/request_human/complete_task, run-JWT, минимальные права). Этот — админская плоскость для человека+Клода СНАРУЖИ (создание команд), авторизация — общий bearer дашборда.
- **Ничего не изобретаем заранее**: MCP-сервер — тонкая обёртка над теми же endpoint'ами, что использует UI итерации 5 (workspace wizard, agent CRUD). Предпосылки: итерация 5 (API создания workspace/агентов) + шаблоны команд (8+). «Клод-тимлид» не запускает прогоны и не двигает тикеты — он только собирает команду; исполнение остаётся за пайплайном.
- Дальний прицел: тот же сервер — точка входа для «декомпозитора» (эпик→тикеты), от которого мы пока осознанно отказались; если когда-нибудь вернёмся — это будет тулза здесь, а не агент внутри пайплайна.

Критерии готовности итераций 1–4 — DoD Phase 0 из [roadmap.md](roadmap.md), итераций 5–6 — DoD Phase 1; итерация 7 — внедрение (критерий: все 6 агентов на BRIGADIR, Jira Automation отключена). Детальная спека — [spec.md](spec.md) §0.x–1.x с поправками из этого файла.

## Модель для команды

- Оркестратор — на общей машине/VPS в своей инфре; Jira — выделенный бот-аккаунт (действия агентов атрибутируются боту).
- Исполнение: старт — подписка Max владельца на его машине (личный пайплайн); для общего командного раннера — командный API-ключ Anthropic со spend cap (~$0.5–2/прогон на Sonnet 5).
